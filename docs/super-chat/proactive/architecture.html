Proactive layer: architecture

How the assistant decides, unasked, that something deserves the person's attention, and prepares the work. Event-driven, one decision run per wake, memory-aware, read-and-draft only. ADRs 0035–0040.

code (deterministic)LLM callruns on the person's hostperson-facing

1 · System overview

Two planes. The engine (one per deployment, Postgres) owns state, scheduling and every decision. The person's host (a container per person) runs agent loops and holds files and the search index. LLM calls happen in three places only: the Judge (engine, no tools), the wake run (host, with tools), and the background passes that write memory and topics.

Found and fixed today: memory was invisible to background code

  • The server never registered its memory service in the runtime (only tests did). The chat itself was fine: its profile block, tools and upkeep get the service passed explicitly.
  • Everything that read the global got nothing: Dreaming and People nightly passes never ran (since at least 17 Oct), the person's own organisation was always empty, the brief and the Lookout had no memory, account deletion left the claim search index stale.
  • Fixed in judge-memory (3b58c11fb): registered at server start, cleared at shutdown. Deployed to the train stack.

5 · Relevance: hard filter, then the Judge

code Hard filter: things that can never matter

  • Own mail; no-reply / bounce sender; List-Id, List-Unsubscribe, Precedence: bulk|list|junk; auto-reply headers or subject; calendar accept with no text
  • Person not in To/Cc; the person replied last in the thread; older than 14 days
  • "Not useful" mutes (topic, or sender on a topic); stale (mail: end of next working day; promise: its date)
  • Word/person matching still runs, as a hint only: strong (shared thread/file/meeting) · medium (watched person + ≥1 term) · weak (≥2 terms, or watched sender). Terms in ≥5% of the person's mail, on ≥3 topics, or the own org don't count.

LLM Judge (ADR 0040)

  • One batched call per wake (25 signals per call) on the Conversation's model (its pin, else Foundation pick), over its own connection; no tools.
  • Input, fenced as data: signals + code hint · open topics (where it stands, dated open lines, watch list) · memory pack · the person's own messages from the last 24 h (≤2,000 chars).
  • Output per signal: relevance 0–100 · topic · urgency now|today|later · why.
  • < 40 → never starts a message, waits for the brief. now → skips learned timing only.
  • Model down or unreadable → fallback from the hint: 70 / 55 / 40 / 20.
  • Live, 22:30: sales pitch 8 "cold pitch, no link to open work"; Dana's translator quote 82 today "approve before Friday".

6 · "A good time": the timing model

Decided per topic, by code, every wake. Hard ceilings first, then what was learned from behaviour. Never from ratings.

good(t, topic) = reach_rules.allow(t, topic, senders) # pause · mute · only-for (the person's words) ∧ in_window(t) # hours rule, else outside quiet hours, else Mon–Fri 08–18 ∧ sent_today < cap(level) # off 0 · low 1 · normal 3 · high 6 · brief not counted ∧ no message on topic in last 3 h ∧ ( urgent ∨ ¬learned ∨ rate(cell) unknown ∨ rate(cell) ≥ 0.35 ∨ (exploring ∧ rate(cell) ≥ best rate) ) cell = day_part × weekday|weekend × chatting|not # 4 × 2 × 2 = 16; night 23–06 has none outcome = acted_on (or topic picked ≤3 h) → yes 1 · opened → yes ½ · unseen 24 h → no ½ · else 0 weight = 0.5 ^ (age / 14 days) overall = (Σyes + 1) / (Σyes + Σno + 2) rate = (yes + 2·overall) / (yes + no + 2) if yes + no ≥ 1, else unknown learned = events on ≥ 4 distinct days; exploring = nothing sent for 3 working days

Properties to know

  • Optimistic: an unknown cell passes. It takes about three ignored messages in one cell before it closes.
  • "Shown" and "seen without action" add nothing; only acting, opening and ignoring move a cell.
  • "Chatting" = a turn is running right now (read live, no presence history stored).
  • Held → next_good_slot scans 15-minute steps up to 8 days; a reach-rule change re-wakes held signals at once.

9 · Known gaps

Memory

  • commitment claims have no dedicated writer; no proactive part reads commitments, projects or decisions directly.
  • Journal and STATE.md are never read by the proactive layer (only via recall).
  • Daily notes never reach the Conversation.
  • The claim search index has no rebuild path outside tests.

Decision

  • Topic grouping is the quiet pass's call; no merge of near-duplicate topics.
  • Timing is optimistic on unknown cells; "seen, no action" teaches nothing.
  • No urgent signal kinds yet (meetings soon need the calendar source).
  • Mail is a dev file mailbox; Microsoft 365 / Google connectors are ADR 0039, not built.
